A minimal but complete MLOps pipeline: train a model, track the experiment, serve it behind a REST API, containerize it, and auto-build/push on every merge to `main`.

## Pipeline overview

```
train.py ──log params/metrics/model──▶ MLflow
   │
   ▼
models/model.joblib ──loaded at startup──▶ api.py (FastAPI)
   │
   ▼
Dockerfile ──multi-stage build (trains inside the image)──▶ container image
   │
   ▼
.github/workflows/deploy.yml ──on push to main──▶ test → build → push to Docker Hub
```

## What's actually in this repo

- **`train.py`** — trains a `RandomForestClassifier` on the Iris dataset, logs params/metrics/model artifact to MLflow, and saves a deployable `model.joblib` + `metadata.json`
- **`api.py`** — FastAPI service with `/health`, `/model-info`, `/predict`, and `/predict-batch` endpoints, validated with Pydantic
- **`tests/test_api.py`** — pytest suite covering health check, valid/invalid input, and batch prediction
- **`Dockerfile`** — multi-stage build: trains the model in the build stage, copies only the artifact + serving code into a slim runtime image
- **`docker-compose.yml`** — spins up the API alongside an MLflow UI for local development
- **`.github/workflows/deploy.yml`** — CI/CD: runs tests on every push/PR, then builds and pushes a Docker image to Docker Hub on merges to `main`

## Setup — local

```bash
git clone https://github.com/<your-username>/mlops-pipeline.git
cd mlops-pipeline
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

python train.py                    # trains model, logs to ./mlruns
mlflow ui                              # optional: view experiment at localhost:5000

uvicorn api:app --reload             # serves at localhost:8000/docs
pytest                                  # run the test suite
```

## Setup — Docker

```bash
docker compose up --build
# API:    http://localhost:8000/docs
# MLflow: http://localhost:5000
```

## Example request

```bash
curl -X POST http://localhost:8000/predict \

  -d '{"sepal_length": 5.1, "sepal_width": 3.5, "petal_length": 1.4, "petal_width": 0.2}'
```

## CI/CD

On every push/PR: install deps → train a fresh model → run pytest. On push to `main`: additionally build the Docker image and push it to Docker Hub, tagged with both `latest` and the commit SHA. Requires `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` set as repo secrets.

## Tech stack

`MLflow` · `FastAPI` · `Docker` · `scikit-learn` · `GitHub Actions` · `pytest`

## Possible extensions

- Swap the toy Iris dataset for a real production dataset with a proper feature store
- Add a model registry stage (MLflow Model Registry) with staging/production promotion instead of always deploying the latest trained model
- Add drift monitoring on incoming prediction requests
- Deploy the pushed image to a real target (ECS, Cloud Run, Kubernetes) as a final CD step

### Resume bullet points

- Built an end-to-end MLOps pipeline covering model training, experiment tracking (MLflow), REST API serving (FastAPI), containerization (Docker), and CI/CD (GitHub Actions)
- Designed a multi-stage Dockerfile that trains the model during image build and ships only the trained artifact + serving code in the runtime image, minimizing final image size
- Set up a GitHub Actions workflow that runs automated tests on every PR and auto-builds/pushes a versioned Docker image on merge to main

### Recruiter talking points

- **What it demonstrates:** thinking beyond "train a model in a notebook" to how a model actually gets tracked, tested, packaged, and shipped.
- **Design decisions worth discussing:** why experiment tracking matters even for small projects; multi-stage Docker builds and why they reduce image size/attack surface; why the CI pipeline trains a fresh model before running API tests (catches integration issues, not just unit-level ones).
- **What you'd improve at scale:** model registry with staged promotion instead of always-deploy-latest, canary/blue-green deployment, monitoring for data/prediction drift, separating training infra from serving infra.
